## Phase 1 Core Principles

### I. Spec-Driven Development (NON-NEGOTIABLE)
Spec-Driven Development is mandatory and non-negotiable for all work:
- No code may be written or modified without prior approved specifications, implementation plan, and task breakdown
- All implementation must be traceable to explicit specifications
- Manual coding by humans is prohibited; all code must be generated by agents based on approved artifacts
- Prioritize readability, maintainability, and clarity over brevity or optimization
- Workflow: Specifications → Plan → Tasks → Approval → Implementation

### II. Phase 1 Scope and Technical Constraints (IMMUTABLE)
This phase is strictly limited to a standalone console application with the following hard constraints:
- **Console-based CLI interface only** - No GUI, no web interface, no REST APIs
- **In-memory storage exclusively** - No file I/O, no JSON persistence, no databases (sqlite3, PostgreSQL, etc.)
- **No web frameworks** - No Flask, Django, FastAPI, HTTP servers, or network communication
- **No authentication** - No user management, session handling, or access control
- **No external integrations** - No AI agents, MCP tools, OpenAI SDK, or external services
- **No containerization** - No Docker, Kubernetes, orchestration, or cloud constructs
- **Python 3.13+ only** - External dependencies permitted only if explicitly justified and minimal (standard library preferred)

**Violations of these constraints result in automatic Phase 1 disqualification.**

### III. Code Quality and Type Safety (MANDATORY)
All code must meet professional quality standards:
- **Full type hints required** on all public functions, methods, classes, and variables
- **Task model implemented as dataclass** with proper type annotations
- **Strict separation of concerns** with modular structure:
  - `models.py` - Data models (Task dataclass)
  - `storage.py` - In-memory storage logic
  - `cli.py` - CLI interface and user interaction
  - `main.py` - Entry point
- **No mutable global state** - Storage must be passed explicitly between components
- **Pure functions preferred** - Functions should be pure where feasible
- **Comprehensive docstrings** for modules, classes, and public functions (Google or NumPy style)
- **PEP 8 compliance** - All code must conform to PEP 8 style guide
- **Defensive programming** - Input validation and clear error messaging required

### IV. Test-Driven Development (NON-NEGOTIABLE)
Testing is mandatory and precedes implementation:
- **TDD workflow**: Write tests → Get approval → Tests fail (red) → Implement → Tests pass (green) → Refactor
- **Red-Green-Refactor cycle** strictly enforced
- **Minimum 80% code coverage** required for all modules
- **Test all CRUD operations**: Create, Read, Update, Delete
- **Test edge cases**: Empty list, invalid IDs, invalid input, boundary conditions
- **Test error handling**: Invalid operations, user input validation
- **Use pytest framework** with clear, descriptive test names
- **Tests must be runnable** with `pytest tests/` from project root

### V. Command-Line Interface Standards
User experience matters even in console applications:
- **Intuitive menu or command system** - Clear navigation and command structure
- **Clear, concise prompts** - User knows what to enter at each step
- **Success/error feedback** - Immediate confirmation of actions
- **Task listing format** - Display: ID | Status (✓/○) | Title | Description
- **Readable output** - Well-formatted, aligned, easy to scan
- **Graceful error handling** - Invalid inputs handled with helpful messages
- **Confirmation prompts** - Required for destructive operations (delete, clear all)
- **Exit option** - Always provide clear way to exit application

### VI. Task Tracking and Traceability
Every code change must be traceable to approved tasks:
- **Task ID references required** - All code modifications must include comment referencing originating task ID
  ```python
  # Task T-003: Implement delete todo functionality
  def delete_todo(storage: TodoStorage, todo_id: int) -> None:
      """Delete a todo by ID."""
      ...
  ```
- **Acceptance criteria verification** - Each task implementation must satisfy all acceptance criteria
- **File change tracking** - Document which files were created/modified for each task

# PHASE 2: Full-Stack Web Application 🔄 ACTIVE

**Status**: 🔄 Active Development
**Version**: 2.0.0
**Started**: 2025-12-29
**Target**: Multi-user web application with authentication and persistent storage

## Phase 2 Core Principles

### I. Spec-Driven Development (NON-NEGOTIABLE)
Spec-Driven Development is mandatory and non-negotiable for all work:
- No code may be written or modified without prior approved specifications, implementation plan, and task breakdown
- All implementation must be traceable to explicit specifications
- Manual coding by humans is prohibited; all code must be generated by agents based on approved artifacts
- **Full traceability required**: every line of code must map back to a specific section in spec.md, plan.md, or tasks.md
- Prioritize **security, maintainability, type safety, and clean architecture** over rapid prototyping
- Workflow: Specifications → Plan → Tasks → Approval → Implementation

**Rationale**: Spec-Driven Development ensures that all development work is intentional, traceable, and aligned with project goals. This methodology prevents scope creep, maintains consistency, and enables effective collaboration between humans and AI agents.

### II. Phase 2 Scope and Technical Constraints (IMMUTABLE)
This phase delivers a secure, multi-user, persistent full-stack web application with the following hard constraints:
- **Frontend**: Next.js 16+ with App Router, TypeScript, Tailwind CSS only
- **Backend**: Python FastAPI only
- **ORM**: SQLModel only
- **Database**: Neon Serverless PostgreSQL only
- **Authentication**: Better Auth with JWT tokens (shared BETTER_AUTH_SECRET) only
- **No console/CLI remnants** from Phase 1
- **No AI agents, MCP tools, Kafka, Dapr, Docker, or Kubernetes concepts**
- **No external libraries** beyond those explicitly required by the tech stack

**Violations of these constraints result in automatic Phase 2 disqualification.**

**Rationale**: These constraints ensure a consistent, secure, and maintainable architecture that aligns with hackathon requirements. The prescribed stack provides modern, production-ready tools while maintaining simplicity and avoiding over-engineering.

### III. Architecture and Security Standards (MANDATORY)
All architectural decisions must prioritize security, user isolation, and clean separation:
- **Monorepo structure** with clear separation: /frontend, /backend, /specs
- **Stateless authentication** using JWT tokens exclusively
- **Backend JWT verification** on every request - no exceptions
- **User isolation enforced**: All queries MUST filter by authenticated user_id
- **Database-level user isolation**: tasks table MUST have user_id foreign key
- **Protected API endpoints**: All endpoints under /api/ require valid JWT (401 Unauthorized without token)
- **Environment variables mandatory** for all secrets (BETTER_AUTH_SECRET, DATABASE_URL)
- **No hardcoded secrets** - use .env files with .env.example templates

**Rationale**: Security is non-negotiable in multi-user web applications. Stateless JWT authentication enables horizontal scaling while maintaining session security. User isolation prevents data leaks and ensures compliance with privacy requirements.

### IV. Code Quality and Type Safety (MANDATORY)
All code must meet professional quality standards with full type safety:
- **Full type safety required**: TypeScript in frontend, Pydantic/SQLModel type hints in backend
- **Modular design** with strict separation of concerns
- **Server Components by default** in Next.js (use Client Components only when necessary)
- **Clean API client abstraction** in frontend (/lib/api.ts)
- **Comprehensive error handling** with meaningful HTTP status codes (400, 401, 404, 500, etc.)
- **Defensive validation** of all inputs at system boundaries
- **Consistent naming, formatting, and documentation** across codebase
- **Task ID references** in comments where applicable (e.g., `// Task T-042: Implement user signup`)
- **No mutable global state** - use dependency injection and React state management
- **ESLint/Prettier for frontend**, **Black/Ruff for backend** (or equivalent formatters)

**Rationale**: Type safety catches errors at compile time, reducing runtime failures. Modular design enables testing, maintenance, and team collaboration. Defensive validation prevents security vulnerabilities like injection attacks.

### V. Frontend Standards (MANDATORY)
User interface must be responsive, professional, and secure:
- **Responsive UI** using Tailwind CSS exclusively
- **Authentication flows**: signup, login, protected routes (middleware), logout
- **Todo dashboard** displaying only authenticated user's tasks
- **Real-time feedback**: loading states, success/error messages, optimistic updates
- **Secure JWT storage**: httpOnly cookies preferred via Better Auth configuration
- **No inline styles** - use Tailwind utility classes or CSS modules
- **Accessibility standards**: ARIA labels, keyboard navigation, semantic HTML
- **Error boundaries** for graceful error handling
- **Form validation** with clear user feedback

**Rationale**: Modern web applications require responsive design for all devices. Better Auth's httpOnly cookies prevent XSS attacks on tokens. Real-time feedback improves user experience and reduces support requests.

### VI. Backend Standards (MANDATORY)
API design must be secure, performant, and maintainable:
- **JWT verification middleware** applied globally (no endpoint bypasses)
- **Dependency injection** for database session management
- **SQLModel models** reflecting exact database schema with relationships
- **Routes organized logically**: /auth (signup, login), /tasks (CRUD)
- **HTTP exceptions** for error cases (HTTPException with status codes)
- **Request/response validation** using Pydantic models
- **Database transactions** for multi-step operations
- **Proper HTTP methods**: GET (read), POST (create), PUT/PATCH (update), DELETE (delete)
- **API versioning** if breaking changes anticipated (/api/v1/)
- **Logging and monitoring** for debugging and observability

**Rationale**: Middleware ensures consistent authentication across all endpoints. SQLModel provides type-safe database operations. Proper HTTP semantics enable REST client compatibility and caching strategies.

### VII. Specification and Documentation Compliance (MANDATORY)
Documentation must be comprehensive and up-to-date:
- **/specs folder** must contain organized, up-to-date specifications:
  - spec.md (feature requirements)
  - plan.md (technical architecture)
  - tasks.md (implementation tasks)
  - Subdirectories for API contracts, database schema, UI components as needed
- **Multiple CLAUDE.md files** (root, frontend/, backend/) providing clear context for agents
- **README.md** must include:
  - Project title and Phase 2 description
  - Local development setup instructions (Node.js, Python, database)
  - Environment variable configuration
  - How to run frontend (`npm run dev`)
  - How to run backend (`uvicorn main:app --reload`)
  - How to run tests
  - Deployment instructions
- **API documentation** using FastAPI's automatic OpenAPI docs (/docs endpoint)
- **Component documentation** for reusable React components

**Rationale**: Comprehensive documentation enables onboarding, troubleshooting, and knowledge transfer. Up-to-date specifications ensure alignment between design and implementation. CLAUDE.md files guide AI agents through complex codebases.

### VIII. Test-Driven Development (NON-NEGOTIABLE)
Testing is mandatory and precedes implementation:
- **TDD workflow**: Write tests → Get approval → Tests fail (red) → Implement → Tests pass (green) → Refactor
- **Red-Green-Refactor cycle** strictly enforced
- **Minimum 80% code coverage** required for both frontend and backend
- **Frontend tests**: Jest + React Testing Library for components, Playwright/Cypress for E2E
- **Backend tests**: pytest for unit/integration tests, TestClient for API routes
- **Test authentication flows**: signup, login, protected route access, logout
- **Test user isolation**: verify users can only access their own tasks
- **Test edge cases**: empty states, invalid inputs, network errors
- **Test API contracts**: request/response validation, error handling
- **Tests must be runnable**: `npm test` (frontend), `pytest tests/` (backend)

**Rationale**: TDD ensures code correctness before deployment. High coverage catches regressions early. Testing user isolation prevents data leaks that could lead to security breaches or compliance violations.

### IX. Task Tracking and Traceability (MANDATORY)
Every code change must be traceable to approved tasks:
- **Task ID references required** in code comments for all implementations
  ```typescript
  // Task T-023: Implement protected route middleware
  export async function middleware(request: NextRequest) {
    // ...
  }
  ```
  ```python
  # Task T-035: Implement JWT verification dependency
  async def get_current_user(token: str = Depends(oauth2_scheme)) -> User:
      # ...
  ```
- **Acceptance criteria verification** before marking task complete
- **File change tracking** in task completion notes
- **Cross-references** between related tasks using task IDs

**Rationale**: Traceability enables code archaeology (understanding why code exists), impact analysis (which tasks affect which code), and audit trails for compliance requirements.

## Phase 2 Agent Conduct Rules

### Approval Gates (STRICTLY ENFORCED)
Agents must respect approval gates at each phase:
1. **Specification Phase**: Create spec.md → Human approval required
2. **Planning Phase**: Create plan.md → Human approval required
3. **Task Breakdown Phase**: Create tasks.md → Human approval required
4. **Implementation Phase**: Execute tasks → Only after all approvals

**Agents must not proceed to implementation without explicit approval of updated specifications, plan, and tasks for Phase 2.**

### Implementation Rules
- **Stop on ambiguity** - Halt and request clarification on any unclear requirement
- **Justify Phase 2 changes** - Every modification must be justified against Phase 2 requirements
- **Task ID comments** - Every code modification must reference originating task ID
- **Acceptance criteria** - Verify all criteria met before marking task complete
- **No scope creep** - Only implement what's specified in approved tasks
- **Security first** - Never compromise on JWT verification or user isolation
- **Validation after each task** - Run tests after completing each task

### Source of Truth Hierarchy
When conflicts arise, follow this precedence:
1. **Constitution** (this file) - Immutable principles and constraints
2. **Specifications** (spec.md) - What the feature does (user perspective)
3. **Plan** (plan.md) - How the feature will be built (technical perspective)
4. **Tasks** (tasks.md) - Step-by-step implementation breakdown
