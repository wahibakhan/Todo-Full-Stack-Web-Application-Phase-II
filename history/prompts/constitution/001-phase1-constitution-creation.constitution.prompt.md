## Prompt

/sp,constitution # Phase 1 Constitution
## Immutable Principles and Standards for Panaversity Hackathon II

### 1. Core Development Principles
- Spec-Driven Development is mandatory and non-negotiable.
- No code may be written or modified without prior approved specifications, implementation plan, and task breakdown.
- All implementation must be traceable to explicit specifications.
- Manual coding by humans is prohibited; all code must be generated by agents based on approved artifacts.
- Prioritize readability, maintainability, and clarity over brevity or optimization.

### 2. Phase 1 Scope and Technical Constraints
This phase is strictly limited to a standalone console application:
- Console-based CLI interface only
- In-memory storage exclusively (no file I/O, no JSON persistence, no database)
- No web frameworks, HTTP servers, REST APIs, or network communication
- No authentication, user management, or session handling
- No integration with AI agents, MCP tools, OpenAI SDK, or external services
- No containerization, orchestration, or cloud-related constructs
- Python 3.13+ only; external dependencies permitted only if explicitly justified and minimal (standard library preferred)

### 3. Code Quality and Architectural Standards
- Full type hints required on all public functions, methods, classes, and variables
- Task model must be implemented as a dataclass
- Strict separation of concerns with modular structure (e.g., models, storage, CLI logic, entry point)
- No mutable global state; storage must be passed explicitly between components
- Functions should be pure where feasible
- Comprehensive docstrings for modules, classes, and public functions
- Inline comments must reference originating task IDs where applicable
- All code must conform to PEP 8
- Defensive programming required: input validation and clear error messaging

### 4. Command-Line Interface Standards
- Intuitive, user-friendly menu or command system
- Clear, concise prompts and success/error feedback
- Task listing must display ID, completion status indicator, title, and description in readable format
- Graceful handling of invalid inputs and edge cases
- Confirmation prompts required for destructive operations (e.g., delete)

### 5. Project Structure and Documentation Compliance
- Exact adherence to defined repository layout with dedicated /specs and /src directories
- All decisions and changes must originate from documented specifications and tasks
- README.md must include clear setup and running instructions

### 6. Agent Conduct Rules
- Agents must not proceed to implementation without explicit approval of specifications, plan, and tasks
- Every code modification must include a comment referencing its originating task ID
- Agents must halt and request clarification on any ambiguity
- Source of truth hierarchy: Constitution > Specifications > Plan > Tasks
